|---|---|
| **In** | Item dicts ({"text": ..., "image": ...}) handed in by the caller -- docpipe/chunking/embedding.py on the batch side, docpipe.inference on the query side -- plus the EMBEDDING_* environment variables read by docpipe/embedding/config.py. |
| **Out** | Lists of float vectors returned to that caller. The package writes nothing to disk, to the database, or to the FAISS index itself -- storing what it returns is the caller's job. |
| **Resumes on** | Nothing here resumes or needs to be redone on its own terms: embed() and embed_one() are plain functions of their input, so which items get (re-)embedded is decided entirely by what the caller sends, not by anything in docpipe/embedding. |

`docpipe.embedding` turns item dicts (`{"text": ...}` or `{"text": ..., "image": ...}`) into vectors, and it is the one interface both sides of this pipeline use for that: the batch pass that builds the corpus (`docpipe/chunking/embedding.py`) and the query path that reads it back (`docpipe.inference`). Both go through `get_embedder()`, which hands back something offering `.embed()` and `.embed_one()`, and neither caller has to know or care whether the vectors on the other end came from a GPU in the same process, an HTTP endpoint, or something a deployment wired in itself. Which of the three a given machine uses is set by `EMBEDDING_BACKEND`, not by code: a laptop without a GPU points at an endpoint, a compute node loads the model, and the caller's own code never changes.

The package itself is stateless: it reads item dicts in and returns lists of floats out, and that is the whole contract. Storing the result is somebody else's job -- the batch caller writes the six embedding types listed in the README (`section_text`, `section_title`, `table_text`, `table_vl`, `figure_text`, `figure_vl`) into the `Embeddings` table and the FAISS index, this package never touches either. Configuration lives in `docpipe/embedding/config.py`: `EMBEDDING_BACKEND` picks `local`, `api`, or an import path; `EMBEDDING_MODEL` defaults to `Qwen/Qwen3-VL-Embedding-8B` at 4096 dimensions (`EMBEDDING_DIM`); `EMBEDDING_MAX_TOKEN_LENGTH` defaults to 16384; `EMBEDDING_BASE_URL` and `EMBEDDING_API_KEY` matter only for the `api` backend.

Two things in `local.py` are easy to get wrong by reading `__init__` alone. First, the model is not loaded there -- it is loaded lazily, on the first call to `embed()`, behind a check-lock-check rather than a single check. That shape exists because one `LocalEmbedder` instance is shared across threads: without the second check inside the lock, two threads could each see `self._resident is None` at the same time and each start loading their own 8B replica, and a spare replica is not a slowdown, it is GPU memory that nothing gives back. Second, `embed()` calls `self._resident.process(...)`, not `.embed(...)`: the underlying `MultiGPUEmbedder` (from `docpipe.chunking.qwen3_vl_embedding`) speaks `process()` and returns a bf16 tensor, and this method's whole job is translating that into the `embed()` / list-of-floats shape the rest of the package expects. The code's own comment records that calling `.embed()` directly used to raise `AttributeError` -- meaning this backend had never actually run before that translation was fixed -- which is a reason to exercise it after touching this file, not just import it.

A third decision in the same call is quieter and has no runtime guard at all: `normalize` is left at its default on purpose, because the corpus vectors already sitting in the index were written by this same call with that default. Change it and nothing raises. A query embedded that way would simply score against the stored vectors incorrectly instead of failing loudly, which is the opposite of how `api.py` handles its own text/image boundary: an item carrying an image is refused with a `ValueError` before a single request goes out, because the OpenAI embeddings schema has no field for one. The alternative -- quietly embedding just the text half of a `table_vl` or `figure_vl` item -- would return a vector that looks valid and is wrong, so the `*_vl` types simply cannot run on `api`; they need `EMBEDDING_BACKEND=local` or an endpoint that accepts multimodal input.

What each backend costs follows from what it is. `local` costs a GPU and keeps it: `MultiGPUEmbedder` loads once and stays resident, data-parallel across every visible GPU, which is what a batch run of thousands of items wants and is also, in the code's own accounting, 16 GB of card per replica that stays occupied for the life of the process -- there is no unload path here, because giving memory back between calls is a property of one deployment's hardware, not of this package (see `scripts/inference_app/README.md` for where that lives instead). `api` costs network round-trips instead of GPU memory: every call goes out to `EMBEDDING_BASE_URL` through the `openai` client, `EMBEDDING_BATCH_SIZE` items at a time (8 by default). Neither backend retries anything. `api.py` does not catch the request it makes, so a dead endpoint or a rejected model name surfaces as whatever the `openai` client raises, straight to the caller. The one failure it does catch early is a missing `EMBEDDING_BASE_URL`: that raises in the constructor, before any request is attempted, rather than on the first call.

Resuming is not a concept this package has. `embed()` and `embed_one()` are pure functions of their input -- there is no cache, no stamp file, nothing here to delete to force a redo. That responsibility sits with the caller: `docpipe.chunking` treats its database as the record of what has already been embedded and hands this package only the items still missing, so redoing embedding work means changing what the caller sends (or clearing what it checks), never touching `docpipe/embedding` itself.

The remaining defenses are aimed at the extension point rather than at either shipped backend. `get_embedder()` rejects an unrecognized backend name with a message that spells out the three valid forms, instead of failing somewhere deeper. `_from_path()`, which resolves a `"package.module:attribute"` spec, catches the `ImportError` and `AttributeError` that a bad module or class name would raise and re-raises both as a `ValueError` naming the spec that caused it -- so a typo in `EMBEDDING_BACKEND` reads as a configuration problem at the point it was set, not as a traceback several frames into `importlib`. That matters here specifically because the third form is meant to be written by a deployment this repository never runs -- an on-demand, quantized, memory-releasing embedder for an interactive app is the example the module docstring names -- and the person hitting that error is unlikely to be the person who wrote this package.
